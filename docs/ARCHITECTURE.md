# Faultline architecture

Faultline is a set of agents around a blackboard. The blackboard is the `reports/` directory; the contract is `faultline/schemas.py`; the system under test is one Docker Compose project. This document lists the modules, walks through the lifecycle of one experiment, describes the control room that drives it all, explains how a previously unseen repository is onboarded, names the data contracts and states the safety invariants.

## Experiment lifecycle

What happens inside one `faultline run` iteration. Timings come from `config/thresholds.yaml`.

1. **Preflight.** Load `topology.json` and `baseline.json` (refuse if either is missing). Refuse if `reports/STOP` exists or `ACTIVE_EXPERIMENT.json` is present (another run is active). Confirm the target container exists in the compose project and is running, and that every other application service is running too. Confirm required images (`pumba`, `tc`) are present for network faults. Measure the pre-experiment window (20 s): if synthetic success is below 95 %, skip with `status: skipped` and a reason. The probes (`ThingsApiProbe`, `HealthProbe`) have been running since the start of the session.
2. **Plan.** `Planner.candidates()` ranks every applicable, policy-allowed (service, failure) pair: `criticality x 1.5 if untested else 1.0 - 1.5 x times tested + per-failure informativeness (0-0.4) - 0.5 if degrade-only - 1.0 if same target as last run`, plus, when `weaknesses.json` exists, up to +1.0 for the Weakness Scout's predicted severity and +0.5 when the failure type is the one the prediction nominated (at most +1.5). The top five go to the LLM; the answer is validated (index in range, parameters clamped, hypothesis services filtered to known names, rates and seconds bounded). If the LLM is disabled, unreachable or returns nonsense, the top candidate is used with a templated rationale. Operator flags (`--target`, `--failure`, `--param`) bypass ranking but not applicability, policy or clamping. Output: `ExperimentSpec` with `reproduce` commands.
3. **Lock.** Write `ACTIVE_EXPERIMENT.json` with the spec, container name, start time and the hard deadline (start + min(`duration_s`, `max_experiment_seconds`) + `watchdog_grace_seconds`). The Guardian reads this to know what it may restore and when.
4. **Arm the watchdog.** `Watchdog(min(duration_s, 90) + 15 s, handle.revert)` on a daemon `threading.Timer`, i.e. 15 s after the experiment's own deadline and never later than 90 + 15 s. It fires even if the main loop is blocked in a Docker call.
5. **Inject.** `ACTIONS[failure_type](Context)` performs the fault and returns a `Handle`. Record the `injected` timeline event and `injected_at` for the safety window.
6. **Observe loop.** Once per second until `duration_s` elapses, the handle reports `finished()` (Pumba exited, traffic burst ended) or a verdict says abort: evaluate `SafetyMonitor` (operator stop via `STOP` file, trailing-10 error rate > 30 %, trailing p95 > max(3000 ms, 5 x baseline), any service outside `hypothesis.expected_affected` unhealthy 3 checks in a row); write `live.json` with current stats for the dashboard and narrator; append timeline events for health transitions.
7. **Rollback.** `handle.revert()`: idempotent, guarded by a lock, also called from a `finally` block so an exception anywhere above still rolls back. Container faults restart or unpause; partitions reconnect with the original aliases; Pumba helpers are removed and the `tc` qdisc deleted defensively; marked processes are killed and the flood collection dropped; the fill file is removed; the traffic burst is signalled to stop. Disarm the watchdog.
8. **Recovery wait and escalation.** Poll every 2 s for up to `recovery.timeout_seconds` (300 s). Recovered when success >= 95 % and p95 < max(300 ms, 2 x baseline p95) and the target plus every expected-affected service passes its health checks, for 3 consecutive checks; a recovery candidate then has to hold through a 20 s soak, and a relapse resets the wait (finding `relapse_after_recovery`). At 50 % of the timeout (150 s) with no recovery, restart the target; at 80 % (240 s), restart its direct dependents. Each action is appended to `recovery.remediation_actions`. Record `time_to_recover_s`, `outage_duration_s`, `auto_restarted_by_docker`.
9. **Integrity check.** `ThingsApiProbe.integrity_check()`: read the canary's `seq` property back and compare with the last acknowledged write. Lower means `data_loss_suspected`.
10. **Findings and hypothesis validation.** Compute `baseline`, `during`, `after` window stats and per-service `HealthSummary`. Derive findings: `api_impact` (what the synthetic client saw), `safety_abort`, `health_check_masked_failure` (API success below 50 % while the target container stayed up and a service in the blast radius kept answering `/ready` = 200), `dependency_blind_readiness` (the target was down and its expected-affected dependents kept answering `/ready` = 200), `no_automated_remediation` (API success below 50 % but the target stayed `running` and never turned `unhealthy`, so nothing reacted), `manual_restart_required` (escalation acted), `recovery_failed`, `relapse_after_recovery`, `data_loss_suspected`, `cascade_beyond_hypothesis` (affected service not in `expected_affected`), `slow_recovery` (TTR > 1.5 x `expected_recovery_s`), `auto_recovered`. Compare observed max error rate, affected services and recovery time with the hypothesis; set `hypothesis_result.held`.
11. **Report.** Write `experiments/<id>.json` (`ExperimentReport`) atomically; clear `ACTIVE_EXPERIMENT.json`; update `live.json` to idle. Pause 30 s before the next iteration so the next pre-window is clean. Downstream agents (`risk`, `fix`, `scorecard`, `narrate`) run on demand or as part of `demo` and only read the report.

## Control-room architecture

The CLI runs one command and exits. The control room instead keeps state, which is the whole reason it needs a control plane of its own. `faultline/dashboard/control.py` holds all of it; `server.py` is a thin HTTP adapter with no logic beyond routing, JSON and MIME types; the browser renders and nothing more. There is no state in the frontend that matters after a reload, except which experiment rows the operator has expanded.

**The long-lived session.** `ControlPlane.arm()` constructs the same `faultline.cli.Session` the CLI uses — Docker client, topology (loaded from `reports/topology.json` or built if absent), policy, thresholds derived from the baseline, the `ThingsApiProbe` at `probe_rps` (4 req/s) and the `HealthProbe` at `health_interval_s` (3 s) — and keeps it. `disarm()` stops the probes. Jobs that need a live session call `_require_session()`, which arms on demand, so starting an experiment from a cold page works; `GET /api/plan` does the same, which means the planner endpoint has the side effect of starting the probes. An arming failure (no Docker, no Ditto) is caught, recorded in `session.error` and surfaced in the launcher; the page still renders.

**The single-job rule.** Operator actions are `Job`s with an id, a kind (`topology`, `baseline`, `run`, `analyze`, `heal`), a human label, a status and an error. `submit()` takes a lock, refuses with `JobBusy` if one is already running (the server turns that into HTTP 409) and otherwise starts one daemon thread. Only the most recent job is kept. Cancellation is cooperative: `cancel()` sets a `threading.Event` that the run loop checks between experiments and passes to its sleeps, and for a `run` it additionally requests STOP so the in-flight experiment rolls back. This mirrors the injector's own `ACTIVE_EXPERIMENT.json` lock rather than replacing it — both are in force, so a CLI `faultline run` in another terminal still cannot collide with one started from the browser.

**The event log.** `EventLog` is an in-memory ring of 4000 `Event`s, each with a monotonically increasing sequence number, a timestamp, a level (`info`, `success`, `warn`, `error`, `chaos`, `ai`), a source (`system`, `topology`, `planner`, `injector`, `guardian`, `risk`, `fix`, `scorecard`, `probe`) and text. Every agent that the control plane invokes is handed `_logger(source)` as its `log=` callback, so the existing agents narrate into the feed without knowing a UI exists; `infer_level()` guesses the level from the text when the caller does not say. `GET /api/state?since=<seq>` returns only events newer than `<seq>`, at most 300 of them, which makes the feed an append-only delta rather than a list the client re-renders. The log is not persisted: restarting the server empties the narration, while `reports/logs/*.log` and the experiment reports survive.

**The telemetry buffer.** A daemon thread samples once per second (`TELEMETRY_SAMPLE_S`) whenever a session is armed: it asks the probe's `SampleWindow` for stats over the trailing 5 s and appends `{t, success, p95, n}`. The buffer is trimmed to the last 300 s (`TELEMETRY_WINDOW_S`) on read. The same loop maintains the phase bands — `{from, to, phase, experiment_id}` spans, opened when `live.json` reports a non-idle phase and closed when it goes idle again — which is what the chart shades. Resolution is deliberately coarse: the point of the chart is the shape of the fall and the recovery from three metres away, not per-request detail, and 300 one-second points is a payload the browser can re-render every 400 ms without thinking about it.

**The polling contract.** One endpoint, one snapshot, no WebSocket and no server-sent events: `GET /api/state?since=<seq>` returns events, session, job, live run, telemetry, agents, LLM status, topology, baseline, every experiment summary and the scorecard in a single response. The client polls it every 1000 ms when idle and every 400 ms while `run.phase` is not `idle`, skips a poll if one is still in flight, and marks itself offline instead of blanking if a poll fails. Every accessor inside `state()` is wrapped so that one broken section (an unreadable report, a Docker call that hangs) degrades to `null` rather than failing the whole response — the dashboard must never die on a bad request, because it is on a projector.

**Phases.** `_run_state()` derives the live run entirely from `live.json` plus the job in flight: `preflight` is synthesised while a `run` job has a spec but the injector has not written anything yet, `analyzing` while an `analyze` job is running, and otherwise the phase is whatever the injector last wrote — `injecting`, `recovering`, `soaking` or `idle`. `copy.js` maps those onto the seven-step ribbon (`PHASE_INDEX`), with `injecting` lighting the Observe step. Inject and Rollback are ribbon steps rather than reported phases, and `safety.abort_reason` is not written to `live.json`, so an abort reaches the UI with the finished report rather than live.

**Per-agent state.** Separate from the event log, `_agent(name, state, detail)` keeps one row per agent (`idle` / `working` / `done` / `error`, a timestamp and one line of detail) for the pipeline strip. The Guardian's row is not written by the control plane at all: it is derived from the freshness of `guardian.heartbeat.json` (alive if under 15 s old), because the Guardian is a separate process by design.

## Repo onboarding

Everything above is repo-agnostic except one input. The topology mapper's richest signal is a *documented knowledge* file listing the dependencies a deployment never declares: that five services join one Pekko cluster, that the gateway asks `policies` to authorise every request, that the search index is fed by thing events. Compose cannot express any of that. For Eclipse Ditto a human wrote it down in `config/ditto_knowledge.yaml` after reading Ditto's architecture pages. `faultline onboard <repo>` does that reading for any Docker Compose repository, which is what makes the rest of the system repo-agnostic rather than Ditto-specific.

`faultline onboard <repo> [--out DIR] [--compose PATH] [--ref BRANCH] [--cache-dir DIR] [--compare-to FILE] [--dry-run] [--json] [--no-llm]`, implemented in `faultline/onboarding/`, driven by `cli.cmd_onboard`, consumed by `faultline topology --knowledge <file>`.

1. **Resolve the reference.** `source.parse_reference()`: an existing path is local and used in place; a GitHub URL, `owner/name` shorthand or any `git@` / `ssh://` / `http(s)://` reference becomes a clone URL. Anything else is a `SourceError` and the command exits 1 rather than guessing. The repository name, slugified, is the output filename.
2. **Fetch.** `git clone --depth 1 --filter=blob:none` into `<cache-dir>/<slug>` (default `.cache/onboarding/`), optionally at `--ref`. An existing checkout is reused rather than re-downloaded, so the first run needs network and every later run does not. Clone failures delete the partial directory.
3. **Locate the compose file.** `--compose` wins outright. Otherwise an ordered candidate list is tried, deployment paths before the repository root — projects like Ditto keep a toy compose at the root and the real one under `deployment/docker/` — and only then a bounded `rglob` for compose-shaped filenames, skipping `.git`, vendor, test, build and virtualenv directories, ignoring anything more than four path segments deep, and preferring the shallowest shortest match. Finding none is a hard error.
4. **Locate the prose.** The README (the root one preferred over a deployment-local one, because the local copy is usually about running the stack rather than about the product), an nginx config next to the compose file if there is one, and up to six architecture documents chosen by generic filename scoring: an architecture overview outranks `architecture.md`, which outranks a per-service architecture page, which outranks `design` / `concepts` / `overview`, which outranks a how-it-works or getting-started page. ADRs, decision records, changelogs, release notes, migration, contributing and upgrade documents are penalised out of the list entirely, and files under 200 B or over 120 kB are skipped. A missing README or nginx config is a note in the report, not a failure.
5. **Run the existing structural parsers.** `topology.compose.service_nodes()` and `static_edges()` with no knowledge file applied. This is the same code the mapper uses, so the agent starts from exactly what Faultline can already see by itself: the service list, guessed roles, healthcheck ports, network aliases, statefulness, and every edge that `depends_on`, an environment-variable hostname or an nginx `proxy_pass` already declares.
6. **One bounded LLM call.** The prompt carries the per-service facts, the structurally known edges under an explicit instruction not to simply repeat them, the README excerpt (biased toward sections whose titles and opening text look architectural, with licence and contributing sections scored down), the architecture-documentation excerpt labelled per file, and `config/ditto_knowledge.yaml` as a worked example of the required shape and level of detail. The whole prompt is held under `MAX_PROMPT_CHARS` (42 000) by trimming documentation first and the README second, and a provider rejection that looks like a payload or context limit triggers exactly one shrink-and-retry with the documentation halved. The answer must be one JSON object. No model, a disabled model (`--no-llm`), or no usable JSON produces a structural-only knowledge file and a note explaining why — never an exception and never a half-written file.
7. **Validate.** `agent.validate()`, below. The model proposes; code decides what is admissible.
8. **Render and write.** `render_yaml()` emits only the fields that have a value, under a four-line provenance header recording the source repository, the compose file inside it, the generator and model, and the instruction to review the file before trusting it. The destination is `<out>/<slug>_knowledge.yaml` (`--out`, default `config/`); `--dry-run` prints everything and writes nothing. The command returns an `OnboardingReport` (`--json`) with the service list, the structural edge count, the knowledge, every rejection and every note, and with `--compare-to` also prints `compare()` against a hand-authored file.

**Validation: what code refuses to accept.** Every rejection is appended to `OnboardingReport.rejected` and printed, so the operator sees what the model said and what was thrown away.

- Edges naming a service that is not in the compose file are dropped, as are self-edges and duplicate pairs.
- An edge that merely restates a structurally known edge is dropped unless it carries a real reason rather than a placeholder (at least 12 characters of evidence); evidence is whitespace-collapsed and cut at 240 characters.
- A role outside `("datastore", "app", "proxy", "ui", "other")` is rejected, and a role that only agrees with the structural guess is discarded as a no-op rather than written out as an override.
- **A `ui` or `other` override is refused for any service with a `build:` section.** In Faultline those two roles mean *excluded from chaos testing* (`chaos_relevant` is false and the planner will never target the service). A service this repository builds from its own source is the product, so accepting such an override would silently exempt a product service from every experiment. This is the one guard that exists for safety rather than hygiene; `ui` / `other` for an image-only service (Swagger UI, Prometheus, Grafana, cAdvisor, exporters) is accepted.
- `health_port` must parse as an integer in 1–65535, and `infer_health_port()` derives the management port shared by at least two compose healthchecks in code and overrides whatever the model answered.
- `cluster_alias` must be a network alias actually declared in the compose file; otherwise it is dropped.
- `references` keeps only `http`-prefixed strings, at most eight.
- The documented-edge list is capped at `MAX_EDGES` (80).

The result is a `RepoKnowledge` (`faultline/schemas.py`), whose own validators re-check the port range and the role vocabulary, so the file that reaches disk is valid by construction and cannot name a service that does not exist.

**Where the knowledge file is actually consumed.** The schema carries nothing decorative, but the fields are not equally plumbed, and that is worth knowing before trusting a generated file:

- `roles` — `topology.compose.service_nodes()` applies them as role overrides, which set `chaos_relevant` and therefore what the planner is allowed to target.
- `documented_edges` — `topology.compose.documented_edges()` merges them into the graph as `kind: documented` edges. They feed fan-in and transitive dependents, so they change the criticality ranking and therefore the order in which things get broken. This is the field that matters.
- `health_port` — `service_nodes()` uses it as a fallback health port, but only for an `app` service whose image name contains `ditto-`. On any other target the value is generated, validated and recorded, and currently has no effect.
- `cluster_alias` — not read from the knowledge file today. `render.mermaid()` groups the cluster subgraph by its own `DEFAULT_CLUSTER_ALIAS` (`"ditto-cluster"`), and `cli.build_topology()` does not pass the knowledge value through. The agent still derives it, validates it against the real network aliases and scores it under `--compare-to`, so it is correct and inert rather than correct and used.
- `references` — documentation for humans reviewing the file. Nothing reads it.

**Acceptance.** Ditto is the only target with ground truth, so the acceptance test is the generated file against the hand-authored one (`--compare-to`): final graph coverage 9/9, documented-edge F1 0.82, effective role accuracy 1.00, `cluster_alias` and `health_port` exact. The headline is downstream of all of that — layered onto the same compose file, the generated file and the hand-authored file produce an identical criticality ranking across all nine services. The edges the agent "misses" are ones `depends_on` already declares, which it was told not to restate, so the merged graph is complete. Edge-level precision and recall move a little from run to run; the coverage and the ranking are the stable results. On `dockersamples/example-voting-app` it returns zero documented edges, because that compose declares every dependency it has, and it does not hallucinate a Pekko cluster out of the worked example.

**What onboarding does not make generic.** It closes the topology gap and only that. Three things are still Ditto-shaped after a successful onboarding run:

- `faultline/agents/knowledge.py` — the remediation rule library is Ditto-specific prose (gateway, things, policies, MongoDB, the Pekko cluster, issue 1865). Against another target the fix agent falls back to its generic rules and whatever the model adds.
- `config/thresholds.yaml` — the protected-service policy (`mongodb` is degrade-only), the skipped roles and the run limits are written for this stack. A new target needs its own protected list before anything is injected at it.
- `faultline/observe/probes.py` — `ThingsApiProbe` generates synthetic traffic against the Ditto Things API, so the steady-state signal itself is application-specific.

## Data contracts

All in `faultline/schemas.py`. Each blackboard file validates against exactly one top-level model.

| Model | File | Purpose |
|---|---|---|
| `ServiceNode` | in `Topology` | one compose service: image, role (`datastore` / `app` / `proxy` / `ui` / `other`), stateful, entrypoint, health port, memory limit, aliases, chaos relevance, live container state |
| `Edge` | in `Topology` | `src` depends on `dst`, with `kind` (`depends_on`, `env`, `proxy`, `documented`, `observed`) and evidence text |
| `Criticality` | in `Topology` | per-service fan-in, transitive dependents, score, reasons |
| `Topology` | `topology.json` | services, edges, criticality ranking, structural findings; helper methods for dependents and dependencies |
| `WindowStats` | in `Baseline`, `ExperimentReport` | sample count, success rate, p50/p95/p99, per-operation breakdown, status counts |
| `Thresholds` | in `Baseline`, `SafetyOutcome` | absolute abort and recovery limits derived from the YAML floors/factors and the baseline p95 |
| `Baseline` | `baseline.json` | steady-state API stats, per-service health availability, derived thresholds, notes |
| `HealthSummary` | in `ExperimentReport` | per-service alive/ready fractions, whether Docker reported unhealthy, whether the container was seen down |
| `Hypothesis` | in `ExperimentSpec`, `ExperimentReport` | falsifiable prediction: statement, expected affected services, expected max error rate, expected recovery seconds |
| `ExperimentSpec` | transient (also in `ACTIVE_EXPERIMENT.json`) | what will be run: target, container, failure type, clamped parameters, rationale, hypothesis, `planned_by` (`llm` / `deterministic` / `operator`), planner notes, reproduce commands |
| `TimelineEvent` | in `ExperimentReport` | timestamped event with `t_plus_s` |
| `Finding` | in `ExperimentReport`, `RiskAssessment` | code, severity (`info` to `critical`), title, evidence |
| `SafetyOutcome` | in `ExperimentReport` | aborted early, reason and detail, watchdog fired, operator stop, thresholds in force |
| `RecoveryOutcome` | in `ExperimentReport` | recovered, time to recover, outage duration, Docker auto-restart, remediation actions, data integrity result |
| `HypothesisResult` | in `ExperimentReport` | held, observed max error rate, observed recovery, unexpected affected services, notes |
| `ExperimentReport` | `experiments/<id>.json` | the complete record of one experiment: spec fields, baseline/during/after stats, health summaries, recovery, safety, findings, timeline, reproduce, status (`completed` / `aborted` / `failed` / `skipped`) |
| `RiskAssessment` | `risk/<id>.json` | severity 0-10, level, blast radius, user impact, recovery seconds, factor breakdown, findings, summary, production implication, `generated_by` |
| `Recommendation` | in `FixRecommendation` | title, category, effort S/M/L, confidence, rationale, steps, verify, references |
| `FixRecommendation` | `fixes/<id>.json` | recommendations for one experiment, `advisory_only` (always true), `generated_by` |
| `ServiceScore` | in `Scorecard` | per-service score, grade, experiment count, worst success rate, slowest recovery, finding count, notes |
| `Scorecard` | `scorecard.json` | overall score, ranking worst first, experiment total, summary |

Coordination files without a model: `STOP` (presence is the signal; content is reason and timestamp), `live.json` (free-form dict with `updated_at`, written by the injector once per second and the only place the control plane learns the live phase from), `<agent>.heartbeat.json` (free-form dict with `at`), `logs/<agent>.log`, and `experiments/<id>/` (the directory `ExperimentReport.raw_logs_ref` points at: `report.md` plus the last 120 log lines of the target and of every service the hypothesis expected to be affected).

## Safety invariants

These hold regardless of what the LLM, the operator or a failing experiment does.

1. **Scope.** Every container operation goes through `DockerController`, which lists containers by the label `com.docker.compose.project=<FAULTLINE_COMPOSE_PROJECT>`. Containers outside that project cannot be addressed. Helper containers carry `faultline.helper=1` and are the only things Faultline creates.
2. **Code owns the limits.** Thresholds come from `config/thresholds.yaml` and the baseline. The LLM receives candidate indices and parameter bounds, never the thresholds, and its output is clamped into the catalog bounds. A model can make an experiment shorter or lighter, never longer or heavier.
3. **Bounded parameters.** Every catalog parameter has `lo` and `hi`; `clamp()` is applied to LLM and operator input alike; every clamp is noted in the spec's `planner_notes` (printed by `faultline plan`), and the report's `parameters` hold the clamped values.
4. **Bounded time.** Hard cap of `max_experiment_seconds` (90 s) on the fault, enforced by the observe loop, plus an independent `Watchdog` 15 s after the experiment's deadline (at most 90 + 15 s) that calls `revert()` from its own thread. Recovery waiting is capped at `recovery.timeout_seconds` (300 s).
5. **Idempotent rollback.** `Handle.revert()` runs at most once (lock + flag) and is safe from any thread. It is called on normal completion, on abort, from the watchdog and from a `finally` block. The Guardian, being a separate process, does not call it; it restores state through its own Docker client instead.
6. **One experiment at a time.** `ACTIVE_EXPERIMENT.json` is the lock; a run refuses to start while it exists. The control room adds a second, independent constraint on top: exactly one job runs at a time per server process, and a second request is refused with HTTP 409 rather than queued.
7. **Do not break a sick system.** Injection is refused when the 20 s pre-experiment window shows less than 95 % success, and `baseline` warns when the steady state itself is below 99 %.
8. **Protected services.** `mongodb` accepts only degrade-only faults unless `--allow-protected` is passed; the override is noted in the spec's `planner_notes` (shown by `faultline plan`). The `ui` role and the observability containers are never targets.
9. **Blast radius is part of the hypothesis.** Any service outside `expected_affected` that fails 3 consecutive health checks aborts the experiment, and any service affected but not predicted produces a `cascade_beyond_hypothesis` finding.
10. **Kill switch from anywhere.** `reports/STOP` is checked every second by the safety monitor and by the Guardian; it is written by `faultline stop`, by `POST /api/stop` (the control room's STOP button and the `Esc` key), or by hand. `POST /api/stop` is deliberately not a job: it is never queued, never blocked by a running job, and always answers 200.
11. **Independent Guardian.** A separate process with its own Docker client that only restores: it restores the experiment's target if it is still down (stopped or paused) past the deadline in `ACTIVE_EXPERIMENT.json` and any other watched container after 20 s down, removes stale helpers and their `tc` qdiscs once that deadline has passed, clears a lock left 30 s past its deadline, on STOP restores everything immediately and reconnects partitioned containers, and never injects.
12. **Advisory only.** No agent has a code path that modifies the compose file, container configuration or Ditto settings. `FixRecommendation.advisory_only` is always `true`.
13. **Reproducible.** Every report carries the shell commands equivalent to the injection under `reproduce`, so any finding can be verified without Faultline.
